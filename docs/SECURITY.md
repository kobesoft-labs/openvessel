# OpenVessel のセキュリティ

## 前提

- ユーザーは **自分のコードを自分のブラウザで** いじる。ランタイム（R）で動くコード（ユーザーのコード・npm の依存）は、ユーザーの持ち物として扱う
- ただし、npm の依存やサイトに入っている外のスクリプトは悪いかもしれない。守りたいのは次の 3 つ
  1. ホストのページ（H）の画面・クッキー・ストレージ
  2. ユーザーの知らないところで外へ通信されること
  3. プレビュー（P）のページから、ランタイムを操られること

## オリジン

| オリジン | 載るもの | 信用 |
|---|---|---|
| H（ホスト） | 埋め込む側のアプリ・OpenVessel のホスト API | いちばん信用する |
| R（ランタイム） | カーネル・プロセス・npm の依存・ユーザーのコード | ユーザーの持ち物。外への通信だけ関所を通す |
| P（プレビュー） | サイトの HTML/JS・サイトが読む外のスクリプト | 信用しない |

3 つは必ず別のオリジンにする。多人数で使うときは P をセッションごとのサブドメインにする。

## 守り

### H を守る

- R・P は別オリジンの iframe。H の DOM・クッキー・ストレージには届かない
- P の iframe は `sandbox`（トップの移動は不可）
- `runtime.html` は CSP の `frame-ancestors` で H だけに絞り、起動時に `location.ancestorOrigins` も確かめる

### 外への通信

- R の文書と Worker には CSP `connect-src 'self'` を付ける。プロセスの `fetch`・`WebSocket` は R の外へ直接出られない
- 出口は R の Service Worker の `/__ov/net` だけ。SW が方針（`src/shared/policy.ts`）を見て、許可されたものだけ本物の `fetch` をする
  - 方針: 用意したセット（npm・fonts・icons・cdn・github）＋ `allow`／`deny` ＋ モード（`ask`・`allowlist`・`allow-all`）
  - `deny` はいつも勝つ。`http:`・`https:` 以外は出さない
- 方針を変えられるのは H だけ。SW は Worker からの「許可」を受けない（送り主が window か確かめる）
- P のページの外への読み込みも、P の SW が同じ方針で絞る
- sw.js 自身には `connect-src 'self'` を付けない（SW が唯一の出口のため）

### P からランタイムを操らせない

- P から使える口は「仮想サーバーへの HTTP / WebSocket」だけ（`http-request`・`ws-*`）。ファイルの読み書き・プロセスの起動・通信の許可はできない
- 中継の iframe（P のオリジン）を P のスクリプトに乗っ取られても、同じ口しか無い
- 許可のダイアログの連打は、同じホストへの問い合わせをまとめる。「このセッションは全部断る」がある

### npm

- **依存の** install のスクリプト（`preinstall`・`postinstall` など）は動かさない。プロジェクト自身の `postinstall`・`prepare` は npm と同じく動かす（ユーザーのコードなので。`--ignore-scripts` で止まる）
- tarball は `integrity`（sha512）を確かめてから展開する。キャッシュから取り出すときも確かめる（R の中のコードがキャッシュを書き換えても効かない）
- packument（版の一覧）はセッションのメモリだけに持つ。R のストレージに残すと、R のコードに毒を入れられるため

## 守らないもの（範囲の外）

- R の中のコード同士の分離（ユーザーのコードと依存は同じ箱で動く。本物の Node と同じ）
- CPU・メモリの使い過ぎ（ブラウザのタブの範囲で止まる。ホストはタブを閉じれば止められる）
- ユーザー自身が「全部許可」にしたあとの外への通信

## 報告

脆弱性は公開の issue ではなく、リポジトリの Security Advisories から非公開で報告してください。
