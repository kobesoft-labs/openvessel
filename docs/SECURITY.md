# OpenVessel のセキュリティ

## 前提

- ユーザーは、自分のコードを自分のブラウザで編集・実行します。ランタイム（R）で動くコード（ユーザーのコードと npm の依存パッケージ）は、ユーザー自身のものとして扱います。
- ただし、npm の依存パッケージや、サイトが読み込む外部のスクリプトには悪意のあるものが含まれている可能性があります。保護の対象は次の 3 つです。
  1. ホストのページ（H）の画面・Cookie・ストレージ
  2. ユーザーが把握していない外部への通信
  3. プレビュー（P）のページからのランタイムの操作

## オリジン

| オリジン | 載るもの | 信頼の度合い |
|---|---|---|
| H（ホスト） | 埋め込む側のアプリ・OpenVessel のホスト API | 最も信頼する |
| R（ランタイム） | カーネル・プロセス・npm の依存パッケージ・ユーザーのコード | ユーザー自身のものとして扱う。外部への通信だけはネットワークポリシーで制御する |
| P（プレビュー） | サイトの HTML/JS・サイトが読み込む外部のスクリプト | 信頼しない |

3 つは必ず別のオリジンにします。複数のユーザーで使う場合は、P をセッションごとのサブドメインにします。

## 対策

### H の保護

- R と P は別オリジンの iframe です。H の DOM・Cookie・ストレージにはアクセスできません。
- P の iframe には `sandbox` を付けています（トップレベルのナビゲーションは不可）。
- `runtime.html` は CSP の `frame-ancestors` で埋め込み元を H に限定し、起動時に `location.ancestorOrigins` も確認します。

### 外部への通信

- R のドキュメントと Worker には CSP `connect-src 'self'` を付けます。そのため、プロセスの `fetch`・`WebSocket` は R の外へ直接通信できません。
- 外部への出口は R の Service Worker の `/__ov/net` だけです。Service Worker がネットワークポリシー（`src/shared/policy.ts`）を確認し、許可されたリクエストだけを実際に `fetch` します。
  - ネットワークポリシーは、プリセット（npm・fonts・icons・cdn・github）、`allow`／`deny`、モード（`ask`・`allowlist`・`allow-all`）で構成されます。
  - `deny` は常に優先されます。`http:`・`https:` 以外のスキームは外部に出しません。
- `localhost`・`127.0.0.0/8`・`::1` など自分のマシンを指す名前は、ネットワークポリシーの設定にかかわらず外部に出しません。curl・wget・npm と P のページからのリクエストは仮想ポートに転送します（実際のマシンには届きません）。
- リダイレクトの場合は、最終的な転送先の URL もネットワークポリシーで確認します。拒否された転送先のレスポンスの内容は返しません（ただし、途中の転送先にはリクエストが届きます。ブラウザが Service Worker に途中のリダイレクトを見せないためです）。
- 許可ダイアログに表示する「誰が」の情報は、カーネルが決めます。カーネル自身（npm・curl・wget）のリクエストにはカーネルだけが知っているトークンを付け、プロセスからのリクエストにはプロセステーブルの pid とコマンドを表示します（プロセスが `npm` を名乗ることはできません）。
- ネットワークポリシーを変更できるのは H だけです。Service Worker は Worker からの許可を受け付けません（送信元が window であることを確認します）。
- P のページから外部への読み込みも、P の Service Worker が同じネットワークポリシーで制限します。カーネルと接続できないときは拒否します（そのまま通すことはしません）。「今回だけ許可」はその 1 回だけ有効です。ネットワークポリシーを変更したときや `clearSession()` を呼んだときは、Service Worker が保持している許可も消えます。
- P のページから外部への WebSocket も、接続する前に P の Service Worker にネットワークポリシーを確認します（差し替えた `WebSocket` を使います。ページが自分で起動した Worker の中の `WebSocket` は対象外です）。
- sw.js 自身には `connect-src 'self'` を付けません（Service Worker が唯一の出口であるため）。

### P からのランタイムの操作の防止

- P から使えるのは「仮想サーバーへの HTTP / WebSocket」と「外部 URL を使ってよいかの確認」だけです（`req`・`body`・`body-end`・`abort`・`ws-open`・`ws-msg`・`ws-close`・`net`）。ファイルの読み書き・プロセスの起動・通信の許可はできません。
- 中継用の iframe（P のオリジン）が P のスクリプトに乗っ取られた場合でも、使えるのは同じメッセージだけです。P の Service Worker は、カーネルとの通信チャネルとデフォルトのポートを、正規の中継（`<プレビューのルート>__ov/relay.html` の iframe）からしか受け取りません。中継の iframe も、プレビューのスコープの外にある親（H）からしか通信チャネルを受け取りません。
- 許可ダイアログが連続して表示されないように、同じホストへの許可リクエストはまとめます。「このセッションではすべて拒否」も選べます。

### npm

- 依存パッケージのインストールスクリプト（`preinstall`・`postinstall` など）は実行しません。プロジェクト自身の `postinstall`・`prepare` は npm と同じく実行します（ユーザーのコードであるため。`--ignore-scripts` で止められます）。
- tarball は `integrity`（sha512）を検証してから展開します。キャッシュから取り出すときも検証します（R の中のコードがキャッシュを書き換えても影響しません）。
- packument（バージョンの一覧）はセッション中のメモリだけに保持します。R のストレージに保存すると、R のコードに改ざんされるおそれがあるためです。

## 対象外

- R の中のコード同士の分離（ユーザーのコードと依存パッケージは同じ環境で動きます。本物の Node と同じです）
- CPU・メモリの過剰な使用（ブラウザのタブの範囲で止まります。ホストはタブを閉じれば止められます）
- ユーザー自身が「すべて許可」にしたあとの外部への通信

## 報告

脆弱性は公開の issue ではなく、リポジトリの Security Advisories から非公開で報告してください。
