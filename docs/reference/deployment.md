# Deployment

[日本語](deployment.ja.md)

This page describes how to run OpenVessel in production. It covers the contents of `dist/`, which
directory goes on which origin, the HTTP headers each origin needs and why, caching, hosts that can't set
headers, serving under a path, per-session preview origins, and example server configurations.

## The three origins

OpenVessel runs on three origins. Each one is a separate site from the browser's point of view.

| Origin | Serves | Loaded as | Holds |
|---|---|---|---|
| Host | your application (and `dist/host/index.js`, usually bundled into it) | the top-level page | your UI and the host API |
| Runtime | `dist/runtime/` | a hidden iframe (`runtime.html`) created by `OpenVessel.boot()` | the kernel worker, the process workers, the network policy checks |
| Preview | `dist/preview/` | a hidden relay iframe (`__ov/relay.html`) plus one iframe per preview | the site being developed, served from virtual ports |

The three must be different origins for the isolation described in [../SECURITY.md](../SECURITY.md) to
hold. The host only warns (`console.warn('OpenVessel: the runtime should be served from its own origin')`)
when the runtime is on the host's origin; nothing refuses to start. A demo you only use yourself can put
all three on one origin (the public demo does, see [GitHub Pages](#hosts-that-cant-set-headers-github-pages));
anything that runs code you don't control should not.

```ts
import { OpenVessel } from 'openvessel';

const vessel = await OpenVessel.boot({
  runtimeUrl: 'https://runtime.example.com/',   // a directory ending in "/", or the runtime.html URL itself
  previewUrl: 'https://preview.example.com/',   // a directory ending in "/"
});
```

`runtimeUrl` is resolved with `new URL('runtime.html', runtimeUrl)` and `previewUrl` with
`new URL('./', previewUrl)` (`src/host/index.ts`). A URL without a trailing slash therefore points at its
parent directory: `https://example.com/runtime` loads `https://example.com/runtime.html`. Give either
the directory with a trailing slash or the full `…/runtime.html` URL.

## What is in `dist/`

`npm run build` (`scripts/build.mjs`) writes `dist/`. Only `dist/runtime/` and `dist/preview/` are
deployed as static files; `dist/host/` is the npm package entry point that your application imports.

### `dist/runtime/` (runtime origin)

| File | What it is | When it is loaded |
|---|---|---|
| `runtime.html` | The runtime iframe's document. Contains `<meta name="openvessel-allowed-hosts" content="*">` | When the host calls `OpenVessel.boot()` |
| `runtime.js` | Classic script (IIFE) for `runtime.html`: origin checks, service worker registration, starts the kernel, hands the host its channel (`src/runtime/runtime.ts`) | With `runtime.html` |
| `sw.js` | The runtime service worker (`src/runtime/sw.ts`): ES module delivery under `/__ov/esm/`, `/__ov/builtin/`, `/__ov/mw/` and `/__ov/esm-error`, the policy-checked outbound proxy `/__ov/net`, `/__ov/ping`, the runtime's own files under each kernel's `/__ov/k/<id>/` prefix, and isolation headers for the runtime's own files | Registered by `runtime.js` with scope `./` |
| `kernel.js` | The kernel, an ES module worker (`src/kernel/index.ts`) | Once per boot, as `new Worker('__ov/k/<id>/kernel.js', { type: 'module' })`: `<id>` is a random kernel id per runtime frame, and the service worker serves the file from `kernel.js` |
| `process.js` | The legacy runtime: the older hand-written Node-compatible layer (`src/node/worker.ts`), one module worker per process | For every `node` process when the VFS file `/etc/openvessel/node` contains `legacy` |
| `node-process.js` | The ported runtime: Node.js's own `lib/` on re-implemented `internalBinding()`s (`src/nodejs/boot.ts`), one module worker per process | By default for every `node` process |
| `nodelib.js` | Node.js v22.23.4's `lib/` (and `deps/`) as source strings, generated by `scripts/gen-nodelib.mjs` (about 4.5 MB). Only written when `vendor/node/` existed at build time | Imported statically by `node-process.js` |
| `ts-strip.js` | sucrase as a classic script; used by the ported runtime for `require(esm)`'s ESM → CommonJS rewrite | Ported runtime, first use; fetched with a synchronous `XMLHttpRequest` and evaluated |
| `amaro.js` | Node's own `amaro` (swc compiled to WebAssembly, embedded in the JavaScript, about 3.4 MB), the version Node bundles | Ported runtime, the first time TypeScript is stripped; synchronous `XMLHttpRequest` |
| `chunks/chunk-<hash>.js` | Code shared by `kernel.js` and `process.js` (esbuild code splitting) | Imported statically by those two |
| `chunks/esm-<hash>.js` | sucrase, split out | Dynamic `import()` the first time the kernel or the legacy runtime strips TypeScript or rewrites ESM |
| `chunks/legacy-<hash>.js` | `@noble/hashes` legacy hashes | Dynamic `import()` by the `md5sum` builtin |
| `compat/index.json` | Index of the compat packages: package name → `{ range, file, integrity, pkg }` | Fetched once by the npm installer (`src/kernel/npm/install.ts`) |
| `compat/<id>-<version>.tgz` | Compat packages (npm tarballs) for packages that only ship native binaries: `pagefind-1.5.2.tgz`, `cn-font-split-7.4.3.tgz`, `resvg-js-2.6.2.tgz` in this build | When `npm install` replaces such a package; integrity-checked (`sha512`) |
| `NODE-LICENSE.txt` | Node.js's license with the notices of its bundled dependencies (ships with `nodelib.js`) | Not loaded; deploy it anyway |
| `AMARO-LICENSE.txt` | amaro's and swc's licenses (ship with `amaro.js`) | Not loaded; deploy it anyway |
| `*.map` | Source maps (`sourcemap: 'linked'`) | Only by developer tools; optional |

The chunk hashes change from build to build; deploy the whole directory, not a list of names.

Which process script a `node` process gets is decided per process start: the kernel reads
`/etc/openvessel/node` and starts `process.js` if the file's trimmed content is `legacy`, otherwise
`node-process.js` (`processScript()` in `src/kernel/index.ts`). The published compatibility numbers refer to
the ported runtime, which needs no setup. To run processes on the legacy runtime instead, write the file
before starting them:

```ts
await vessel.mount({ node: 'legacy' }, { path: '/etc/openvessel' });
```

The kernel keeps two idle workers of the script it last started (`WARM = 2`), so after the first
`node` process the next ones start from an already loaded worker.

### `dist/preview/` (preview origin)

| File | What it is |
|---|---|
| `__ov-sw.js` | The preview service worker (`src/preview/sw.ts`). It is at the top of the preview directory so its default scope covers the whole preview |
| `__ov/relay.html` | The hidden relay iframe's document |
| `__ov/relay.js` | Classic script for the relay: registers `../__ov-sw.js` with scope `../` and hands it the kernel channel (`src/preview/relay.ts`) |
| `__ov/inject.js` | Injected into every HTML page the preview shows: WebSocket tunnelling, and `fetch`/`XMLHttpRequest` path fixing when served under a path (`src/preview/inject.ts`) |
| `*.map` | Source maps; optional |

Every other URL on the preview origin is answered by the service worker from a virtual port, so a preview
site can't use the paths `__ov-sw.js`, `__ov/relay.html`, `__ov/relay.js`, `__ov/inject.js` and
`__ov/open` (relative to the preview directory). See [Preview](preview.md).

### `dist/host/` and `dist/types/`

- `dist/host/index.js` is the host API as an ES module (`package.json` `main`/`exports`). Import it from
  your application; usually it is bundled into it.
- `dist/types/host/index.d.ts` and `dist/types/shared/policy.d.ts` are the TypeScript declarations
  (`package.json` `types`).

`dist/playground/` is the development playground served by `npm run serve`; it is not part of a deployment.

## Headers

### Summary

| Header | Host page | Runtime (`dist/runtime/`) | Preview (`dist/preview/`) |
|---|---|---|---|
| `Cross-Origin-Opener-Policy` | `same-origin` (required) | `same-origin` | `same-origin` |
| `Cross-Origin-Embedder-Policy` | `require-corp` or `credentialless` (required) | `require-corp` | `require-corp`; `credentialless` on `__ov-sw.js` |
| `Cross-Origin-Resource-Policy` | as your app needs (`scripts/serve.mjs` uses `same-origin`) | `cross-origin` | `cross-origin` |
| `Content-Security-Policy` | your own | the runtime CSP below, on every file except `sw.js` | not required |
| `Content-Security-Policy: frame-ancestors` | — | the host origin(s) | — |
| `Service-Worker-Allowed` | — | not required | not required |

This is the header set `scripts/serve.mjs` uses. The same headers are sent on error responses there, too.

The preview's `__ov-sw.js` is served with `credentialless` because the service worker passes the page's
`no-cors` loads (images, classic scripts from other servers) through with its own `fetch()`. Under
`require-corp` such a load fails unless the other server sends `Cross-Origin-Resource-Policy`; under
`credentialless` it is sent without credentials and needs no CORP. A browser without `credentialless`
(Safari) refuses those loads.

### Why each header is needed

#### Cross-origin isolation (COOP + COEP)

System calls block on a `SharedArrayBuffer` with
`Atomics.wait` ([Protocol](protocol.md#synchronous-syscall-channel)), and `SharedArrayBuffer` exists
only in a cross-origin isolated context.

- The host page must be isolated: `OpenVessel.boot()` throws
  `OpenVessel: the host page must be cross-origin isolated (COOP: same-origin, COEP: require-corp or credentialless).`
  when `crossOriginIsolated` is false.
- The runtime document must be isolated too. `runtime.js` first registers `sw.js` (which adds the
  isolation headers to the runtime's files, see [below](#hosts-that-cant-set-headers-github-pages)); if
  the document isn't isolated once the worker controls it, it reloads once (guarded by a
  `sessionStorage` flag). If it is still not isolated, it fails with
  `OpenVessel needs a cross-origin isolated page (COOP: same-origin and COEP: require-corp/credentialless on the host page, and allow="cross-origin-isolated" on the iframe).`
  The host creates the runtime iframe with `allow="cross-origin-isolated"`.
- A document embedded in a COEP page must itself be served with COEP, and a cross-origin one also with
  `Cross-Origin-Resource-Policy: cross-origin`. That is why both `runtime.html` and the preview's
  documents carry COEP and CORP `cross-origin`.
- The kernel and process workers are module workers loaded from the runtime origin; they are served
  with the same headers as every other runtime file.

#### The runtime CSP

The CSP confines what code in the runtime (your project, its dependencies) can reach.
`scripts/serve.mjs` sends:

```text
default-src 'self';
script-src 'self' 'unsafe-eval' 'wasm-unsafe-eval' blob: data:;
connect-src 'self' data: blob:;
worker-src 'self' blob:;
img-src 'self' data: blob:;
style-src 'self' 'unsafe-inline';
frame-ancestors <host origin>
```

| Directive | Why the code needs it |
|---|---|
| `script-src 'unsafe-eval'` | Node's builtins are compiled with indirect `eval` from `nodelib.js` (`compileBuiltin()` in `src/nodejs/boot.ts`); `vm`, CommonJS wrappers, `amaro.js` and `ts-strip.js` are evaluated the same way |
| `script-src 'wasm-unsafe-eval'` | esbuild, rollup, rolldown, lightningcss, amaro (swc) and compat packages run as WebAssembly |
| `script-src data:` | the ported runtime's module loader imports `data:text/javascript,…` modules (`src/nodejs/bindings/module_wrap.ts`); the legacy runtime does for `worker_threads` with `eval` and ES modules |
| `connect-src 'self'` | the point of the CSP: processes can't `fetch` or open a `WebSocket` to anywhere but the runtime origin, so the only way out is `/__ov/net`, which the service worker checks against the network policy |
| `frame-ancestors` | only your host page may embed `runtime.html` |

#### No CSP on `sw.js`

A service worker's own `fetch()` is governed by the CSP delivered with
the worker script. The runtime service worker is the outbound proxy: it makes the real outgoing requests
after the policy allowed them. With `connect-src 'self'` on `sw.js` every allowed request would fail.
`scripts/serve.mjs` drops the CSP for `/sw.js` only.

#### `frame-ancestors` and the runtime's own origin check

The runtime checks who embeds it in three ways:

| Check | Where | Fails with |
|---|---|---|
| CSP `frame-ancestors` | your server | the browser refuses to render the iframe; `boot()` then times out |
| `<meta name="openvessel-allowed-hosts">` in `runtime.html`: origins separated by spaces or commas, `*` = any (the shipped default) | `runtime.js`, against the `origin` of the `openvessel-connect` message | `origin <origin> is not allowed to use this runtime` |
| `location.ancestorOrigins` (when the browser has it) must not have more than one entry | `runtime.js` | `the runtime must be embedded directly by the host page` |

All three surface in the host as a rejected `boot()`: `OpenVessel: <message>` for the last two,
`OpenVessel: runtime did not start in time` (after `timeout`, default 30000 ms) for the first. Edit the
meta tag in your deployed `runtime.html`:

```html
<meta name="openvessel-allowed-hosts" content="https://app.example.com https://staging.example.com">
```

#### Preview origin

The preview's static files need COOP/COEP/CORP as above. Everything the preview
shows comes from its service worker, which adds `cross-origin-embedder-policy: credentialless`,
`cross-origin-resource-policy: cross-origin` and `cross-origin-opener-policy: same-origin` to each
response that doesn't already have them, so a dev server doesn't have to send them, and `credentialless`
lets the site load third-party images and scripts that don't send CORP. Don't put the runtime CSP on the
preview origin; the preview has its own policy check in its service worker
([Preview](preview.md#outbound-requests-and-the-network-policy)).

#### `Service-Worker-Allowed`

This header is not needed. The runtime registers `sw.js` with scope `./` (its own
directory) and the relay registers `../__ov-sw.js` with scope `../` (the preview directory, which is also
the worker script's directory).

### MIME types

| Extension | Type | Notes |
|---|---|---|
| `.html` | `text/html; charset=utf-8` | |
| `.js` | `text/javascript; charset=utf-8` | Required: module workers, `import`, and service worker scripts are refused with a non-JavaScript type |
| `.json` | `application/json` | `compat/index.json`, source maps |
| `.map` | `application/json` | |
| `.tgz` | `application/gzip` or `application/octet-stream` | Read with `fetch().arrayBuffer()`; the type isn't checked |
| `.txt` | `text/plain; charset=utf-8` | license files |

`dist/` contains no `.wasm` files: WebAssembly is either embedded in JavaScript (`amaro.js`), inside
compat tarballs, or installed from npm into the in-memory file system and compiled from bytes. If you
add your own files, serve `.wasm` as `application/wasm`.

## Caching

Derived from how the files are named:

| Files | Advice | Why |
|---|---|---|
| `runtime/chunks/*-<hash>.js` | long-lived, `immutable` | the name changes with the content |
| `runtime/compat/<id>-<version>.tgz` | long-lived | versioned name; verified against `integrity` from `index.json` anyway |
| `runtime/sw.js`, `preview/__ov-sw.js` | `no-cache` | service worker updates must be seen; the runtime registers with `updateViaCache: 'none'` |
| everything else (`runtime.html`, `runtime.js`, `kernel.js`, `process.js`, `node-process.js`, `nodelib.js`, `amaro.js`, `ts-strip.js`, `compat/index.json`, `__ov/*`) | `no-cache` (revalidate with `ETag`/`Last-Modified`) | fixed names whose content changes between releases; `kernel.js` and `process.js` name the hashed chunks of the same build |

`scripts/serve.mjs` sends `cache-control: no-cache` for everything. Responses the service workers make
themselves are not cached: modules from `/__ov/esm/`, `/__ov/builtin/`, `/__ov/mw/` and `/__ov/esm-error`, and `/__ov/net`
responses, carry `cache-control: no-store`.

The npm client keeps verified tarballs in Cache Storage on the runtime origin (cache name
`openvessel-npm-v1`) and re-verifies their integrity when it reads them back; this is per browser and per
runtime origin.

## Hosts that can't set headers (GitHub Pages)

Both service workers add the isolation headers to the files they serve. Headers the server already sent
are kept; the workers only add missing ones.

- The runtime `sw.js` adds `cross-origin-opener-policy: same-origin`,
  `cross-origin-embedder-policy: require-corp` and `cross-origin-resource-policy: cross-origin` to every
  same-origin `GET` under its scope that isn't a `/__ov/…` endpoint. Opaque and status-0 responses are
  passed through.
- The preview `__ov-sw.js` adds `cross-origin-embedder-policy: credentialless`,
  `cross-origin-resource-policy: cross-origin` and `cross-origin-opener-policy: same-origin` to its own
  files (`__ov/relay.html`, `__ov/relay.js`, `__ov/inject.js`, `__ov-sw.js`), the `__ov/open` redirect,
  and every response from a virtual port.

A service worker only controls documents loaded after it is installed. The first load of
`runtime.html` and of `__ov/relay.html` is not controlled by these workers. `runtime.js` registers
`sw.js` and reloads the frame once, so the reloaded `runtime.html` gets the headers from the worker;
that only helps if the frame could load at all, which inside an isolated host page needs COEP and CORP
on the first load. So on a host that sends no headers at all, something else has to make those first
loads isolated. The demo
([openvessel-demo](https://github.com/kobesoft-labs/openvessel-demo)) does it this way:

- The page, `runtime/` and `preview/` are on one origin (GitHub Pages), all under one site directory:
  `runtime/` is a copy of `dist/runtime`, `preview/` a copy of `dist/preview`.
- The page registers its own `coi-sw.js` from the site root. Its scope (the site directory) also covers
  `runtime/` and `preview/`, so until their own workers are installed, `coi-sw.js` adds
  `cross-origin-opener-policy: same-origin`, `cross-origin-embedder-policy: require-corp` and
  `cross-origin-resource-policy: cross-origin` to every same-origin `GET`, including `runtime.html` and
  `relay.html`. Once registered, the runtime's and the preview's workers take over their (narrower) scopes.
- The page reloads itself once after registering `coi-sw.js` (guarded by a `sessionStorage` flag) and
  shows an "unsupported" message if it is still not isolated after that.

```html
<script>
  // GitHub Pages sends no isolation headers: let coi-sw.js add them, then reload once
  if (!crossOriginIsolated && 'serviceWorker' in navigator && !sessionStorage.getItem('ov-coi-reload')) {
    navigator.serviceWorker.register('coi-sw.js').then(() => navigator.serviceWorker.ready).then(() => {
      sessionStorage.setItem('ov-coi-reload', '1');
      location.reload();
    });
  } else sessionStorage.removeItem('ov-coi-reload');
</script>
```

```js
// coi-sw.js
const ISOLATION = {
  'cross-origin-opener-policy': 'same-origin',
  'cross-origin-embedder-policy': 'require-corp',
  'cross-origin-resource-policy': 'cross-origin',
};
self.addEventListener('install', () => self.skipWaiting());
self.addEventListener('activate', (e) => e.waitUntil(self.clients.claim()));
self.addEventListener('fetch', (e) => {
  const req = e.request;
  if (req.method !== 'GET' || new URL(req.url).origin !== location.origin) return;
  e.respondWith(fetch(req).then((res) => {
    if (res.type === 'opaque' || res.status === 0) return res;
    const headers = new Headers(res.headers);
    for (const [k, v] of Object.entries(ISOLATION)) if (!headers.has(k)) headers.set(k, v);
    return new Response(res.body, { status: res.status, statusText: res.statusText, headers });
  }));
});
```

The demo boots with URLs relative to the page:

```ts
const here = new URL('./', location.href);
const vessel = await OpenVessel.boot({
  runtimeUrl: new URL('runtime/runtime.html', here).href,
  previewUrl: new URL('preview/', here).href,
  network: { mode: 'allowlist', presets: ['npm', 'fonts', 'cdn'] },
});
```

Its `build.mjs` copies `dist/runtime` to `site/runtime` and `dist/preview` to `site/preview`, adds an
empty `.nojekyll` (so GitHub Pages serves every file as is), and `deploy.mjs` force-pushes `site/` to the
`gh-pages` branch. Without headers there is also no runtime CSP and no `frame-ancestors`, so this setup
gives up the outbound `connect-src` confinement and the embedding restriction; with one origin it also
gives up the origin separation. Use it for demos only.

## Serving under a path

Both the runtime and the preview may be served from a subdirectory (for example
`https://example.com/demo/runtime/` and `https://example.com/demo/preview/`).

On the runtime origin, the kernel takes its base URL from the directory of `kernel.js` (`RUNTIME_BASE` in
`src/kernel/base.ts`) and each runtime from the directory of its worker script (`node-process.js`,
`process.js`); the service worker strips its scope (and a kernel's `/__ov/k/<id>/` prefix) from request
paths before matching `/__ov/…`. The npm client's `/__ov/net` requests and `compat/` downloads, the
ported runtime's `/__ov/net` and `/__ov/mw/` URLs, and the legacy runtime's `/__ov/esm/`, `/__ov/builtin/`
and `/__ov/net` URLs (also those the kernel writes into the modules it serves) are all relative to that
base. Because `kernel.js` is started as `__ov/k/<id>/kernel.js` and starts the process workers next to
itself, that base is `<runtime directory>/__ov/k/<id>`: the service worker answers the `/__ov/…`
endpoints under it for kernel `<id>` and serves the runtime's own files under it from the runtime
directory, so several runtime frames (tabs, or several `boot()`s on one page) can share the service
worker with a kernel each. A `/__ov/…` request without a kernel prefix goes to the kernel named by its
referrer (a file under a kernel's prefix, or a module that kernel served), else to the kernel that
connected last.

On the preview origin, the service worker's scope is the preview directory. A dev server inside OpenVessel still
serves its site at `/`, so the service worker maps between the two:

- the scope is removed from request paths before they reach the virtual port;
- in HTML pages, root-relative `src`, `href`, `action`, `poster`, `formaction` and `srcset` values get
  the scope prepended, and an import map `{"imports": {"/": "<scope>", "<scope>": "<scope>"}}` is
  inserted with the injected script, so root-relative module specifiers (`/@vite/client`, `/src/…`)
  resolve under the scope;
- root-relative `Location` headers are rewritten the same way;
- `inject.js` wraps `fetch()` and `XMLHttpRequest.prototype.open` so root-relative string URLs get the
  scope too.

URLs built in other ways (for example `new URL('/x', location.href)` passed to `fetch`, or CSS `url(/…)`)
are not rewritten. Serving the preview at the root of its own origin avoids all of this.

## Per-session preview origins

For multi-tenant use, give every session (user, workspace) its own preview origin, for example
`https://<session>.preview.example.com/` ([../SECURITY.md](../SECURITY.md)). Different subdomains are
different origins, so one session's preview pages can't read another's cookies, storage or service
worker state.

- Serve the same `dist/preview/` files on every subdomain (a wildcard DNS record and certificate, one
  server block with a wildcard `server_name`).
- Pass the session's URL as `previewUrl` when booting. The host derives the preview origin from it and
  only accepts relay messages from that origin and that iframe.
- Each subdomain registers its own copy of the preview service worker on first use.
- The runtime origin can be shared: a runtime instance is created per `boot()`, and the host hands the
  kernel the preview channel itself, so the kernel doesn't need to know the preview origin.

```ts
const vessel = await OpenVessel.boot({
  runtimeUrl: 'https://runtime.example.com/',
  previewUrl: `https://${sessionId}.preview.example.com/`,
});
```

## Service worker updates

| | Runtime `sw.js` | Preview `__ov-sw.js` |
|---|---|---|
| Install | `skipWaiting()` | `skipWaiting()` |
| Activate | `clients.claim()` | `clients.claim()` |
| Registration | `register('./sw.js', { scope: './', updateViaCache: 'none' })`, then `reg.update()` | `register('../__ov-sw.js', { scope: '../' })` from the relay |
| Start-up | `runtime.js` waits for `controllerchange` while a worker is installing or waiting, so a page never starts the kernel under an older worker | the relay waits for `navigator.serviceWorker.ready` |
| Update while running | on `controllerchange`, `runtime.js` hands the new worker a fresh channel to the kernel | the new worker asks for a channel when it first needs one |

Both workers keep their channel to the kernel in memory. When the browser stops an idle worker and
starts it again, the worker asks for a new one (`need-kernel-port`): the runtime worker asks
`runtime.html`, the preview worker asks the relay, which asks the host. Requests wait up to 15 seconds
for the channel. State the preview worker keeps in memory (which port each preview page belongs to,
allowed hosts) starts empty again after such a restart. See [Protocol](protocol.md).

## Browser requirements

OpenVessel is developed and tested on Chromium-based browsers (the end-to-end tests drive Chrome). The
code relies on:

- cross-origin isolation, `SharedArrayBuffer` and `Atomics.wait` in workers;
- module workers (`new Worker(url, { type: 'module' })`) and nested workers created from the kernel worker;
- service workers on the runtime and the preview origins, inside cross-origin iframes;
- the iframe `allow="cross-origin-isolated"` permission;
- synchronous `XMLHttpRequest` in workers (ported runtime: `amaro.js`, `ts-strip.js`);
- `<dialog>` for the built-in permission prompt (only when no `onPermissionRequest` is given).

`location.ancestorOrigins` is used when present.

## Example configurations

The configurations below send exactly the header sets above. Replace the host names; `app.example.com`
is the host page.

### nginx

nginx drops server-level `add_header` lines in a `location` that has its own `add_header`, so the shared
headers are kept in snippets and included where needed.

```text
# /etc/nginx/snippets/openvessel-isolation.conf
add_header Cross-Origin-Opener-Policy "same-origin" always;
add_header Cross-Origin-Embedder-Policy "require-corp" always;
add_header Cross-Origin-Resource-Policy "cross-origin" always;

# /etc/nginx/snippets/openvessel-runtime-csp.conf
```

### Node.js (`scripts/serve.mjs`)

The repository's development server is the reference for the header sets. It serves `dist/playground`
(host), `dist/runtime` and `dist/preview` on three ports, `OV_PORT_BASE` (default 5170) and the next two;
`OV_HOST_PORT`, `OV_RUNTIME_PORT` and `OV_PREVIEW_PORT` override each one. It listens on `127.0.0.1` only
and sets `frame-ancestors` to `http://localhost:<host port>`.

## Checklist

- [ ] Host, runtime and preview are three different origins (and preview origins are per session if
      several users share a deployment).
- [ ] The host page sends `Cross-Origin-Opener-Policy: same-origin` and
      `Cross-Origin-Embedder-Policy: require-corp` (or `credentialless`); `crossOriginIsolated` is `true`.
- [ ] Every file of `dist/runtime/` and `dist/preview/` sends COOP `same-origin`, COEP `require-corp`
      and CORP `cross-origin`.
- [ ] Every runtime file except `sw.js` sends the runtime CSP; `frame-ancestors` names your host origin(s).
- [ ] `runtime.html`'s `openvessel-allowed-hosts` lists your host origin(s) instead of `*`.
- [ ] `.js` is served with a JavaScript MIME type.
- [ ] The whole `dist/runtime/` directory is deployed, including `chunks/`, `compat/`, `nodelib.js`,
      `amaro.js`, `ts-strip.js` and the license files.
- [ ] `runtimeUrl` and `previewUrl` end in `/` (or `runtimeUrl` is the `runtime.html` URL).
- [ ] Hashed chunks may be cached long; everything else, the service workers in particular, revalidates.
- [ ] `/etc/openvessel/node` is not set to `legacy`, unless processes should run on the legacy runtime.
