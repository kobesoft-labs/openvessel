# プロセス

[English](processes.md)

このページでは、OpenVessel のカーネルのプロセスを定めます。始まりから終わりまでの流れ、プログラムの見つけ方と
起動のしかた、ファイル記述子と標準入出力、パイプとソケット、シグナル、プロセスグループ、端末（TTY）です。
ソースは `src/kernel/kernel.ts`・`src/kernel/proc.ts`・`src/kernel/io.ts`・`src/kernel/syscalls.ts` です。

カーネル全体は [カーネル](kernel.ja.md)、シェルは [シェル](shell.ja.md)、プロセスの中の Node.js のランタイムは
[Node.js のランタイム](nodejs-runtime.ja.md) で説明しています。

## プロセスの記録

| 項目 | 意味 |
|---|---|
| `pid` | プロセスの番号。カーネル全体で起動した順に 1, 2, 3, …。使い回さない |
| `ppid` | 親の pid。ホストが起動したプロセスと、親を失ったプロセスは 0（init のプロセスは無く、ホストがその役をする） |
| `pgid` | プロセスグループ（[プロセスグループ](#プロセスグループとジョブ制御)） |
| `argv` | 引数。node のプロセスの `argv[0]` は `node`（[argv0](#argv-と-env-と-cwd)） |
| `env` | 環境変数（文字列のふつうのオブジェクト） |
| `cwd` | 作業ディレクトリ（`chdir` のあとは実際のパス） |
| `umask` | ファイルを作るときのマスク。ホストが起動したプロセスは 0o022、それ以外は親から受け継ぐ（[mode と umask](filesystem.ja.md#mode-と-umask)） |
| `nofile` | `RLIMIT_NOFILE`。1024 で、親から受け継ぐ。シェルの `ulimit -n` で変える |
| `runtime` | node のプロセス: プログラムを起動したときに選んだ Node.js のランタイム（[node のプロセスの起動](#node-のプロセスの起動)） |
| `fds` | ファイル記述子の表 |
| `tty` | 制御端末。親から受け継ぐ |
| `kind` | `builtin`（カーネルの中で動く）または `node`（Worker で動く） |
| `title` | `node`、または組み込みのプログラムの名前 |
| `state`・`status` | `running` か `exited`。終了状態 `{ code, signal }` |
| `children` | 子プロセスの pid |
| `handledSignals` | プロセスが受け手を登録したシグナル |
| `threads` | node のプロセスの Node のスレッド（メインスレッドとワーカースレッド） |

ホストの `ps()` と `ps` のプログラムは、動いているプロセスだけを出します（`PID`・`PPID`・`argv`）。

## 始まりから終わりまで

### 起動

`kernel.spawn()` は、次のことを同期で行います。

1. 環境変数（渡されたもの、無ければ親の写し、それも無ければ [既定の環境変数](kernel.ja.md#既定の環境変数)）と、
   作業ディレクトリ（渡されたもの、無ければ親のもの、それも無ければ `/home/user`）を決めます。
2. `argv` をどう動かすかを調べます（[プログラムの見つけ方](#プログラムの見つけ方)）。エラーは、pid を取る前の
   ここで投げます: `ENOENT`（`<cmd>: command not found`）、`EACCES`（`<cmd>: Permission denied`）、
   `ELOOP`（インタプリタのつながりが深すぎる）、`EINVAL`（`argv` が空）。
3. 次の pid を取り、プロセスグループ・制御 TTY・`nofile`・`umask` を決め、渡された標準入出力の記述子を fd 0, 1, 2, … に
   置きます（それぞれ参照を 1 つ増やします）。
4. プログラムを始めます。組み込みならカーネルのイベントループの上で、node のプログラムなら Worker で動かします
   （[node のプロセスの起動](#node-のプロセスの起動)）。

`spawn` のシステムコールは、さらに、渡された `cwd` があってディレクトリであることを調べます（`ENOENT`、
`spawn: cwd <path> does not exist`）。ホストの `spawn` は、`cwd` が無ければ `/home/user` を使い、そのディレクトリが
無ければ作ります。

### argv と env と cwd

- 直接起動した node のプログラム（`node app.js`、または中身が `#!/ov/builtin node` のファイルのパス）は、呼び出し側の
  `argv[0]`（`process.argv0`。たとえば `node`）を保ちます。`execve`/`spawn` は別のもの（`argv0`）を渡せます。
  スクリプトの `#!` の行を通して起動したときは、`argv[0]` は `node` です。移植版ランタイムは `process.execPath` と
  `process.argv[0]` を `/usr/bin/node` とします。
- 環境変数はまるごと渡します。子は、親の環境変数と渡されたものを混ぜません。
- `chdir` はシンボリックリンクを解決します。新しい `cwd` は実際のパスです。失敗すると `ENOENT` か `ENOTDIR` です。

### 終了

プロセスは次のどれかで終わります。

| どう終わるか | 終了状態 |
|---|---|
| node のプロセスが `exit` を呼ぶ（`process.exit`、イベントループの終わり） | `code & 0xff`（`process.exit(300)` は 44） |
| 組み込みのプログラムが値を返す、または `ctx.exit(n)` を呼ぶ | `n` |
| 組み込みのプログラムが例外を投げる | 標準エラーに `<name>: <message>` を出し、1 |
| 組み込みのプログラムが、誰も読まないパイプに書く（`EPIPE`） | 141 |
| シグナルで終わる | `{ code: null, signal }` |
| node のプロセスのメインの Worker が失敗する（`onerror`） | 1 |
| `process.abort()`（移植版ランタイム） | 134 |

node のプロセスが `exit` を呼ぶと、カーネルは片付ける前に、読む側が追いつくのを待ちます。そのプロセスが書いた
パイプをほかのプロセスがまだ読んでいるなら、空になるまで（最大 250 ミリ秒）待ちます。そのプロセスが書くソケットを
ほかのプロセスが読んでいるなら、そのプロセスに `ping` を送り、`pong` を（最大 250 ミリ秒）待ちます。終わろうとして
いるスレッドは、二度と動きません。

そのあと、この順に進みます: ワーカースレッドをすべて止める、fd をすべて閉じる（パイプの読み手は EOF を見る）、
待っているものに知らせる、そのプロセスの TCP の待ち受けと Unix ソケットの待ち受けを放す（ホストに `port-closed` が
届く）、監視と UDP のポートを無くす、子の親を pid 0 にする（もうそのプロセスの子ではなくなる）。

数としての終了状態（`$?` やホストの `exit` のイベントが示すもの）は、コード、またはシグナルなら
`128 + シグナルの番号` です（`SIGTERM` は `143`、`SIGINT` は `130`、`SIGPWR` は `158`）。

終わったプロセスの記録は、プロセスの表に 60 秒残り、そのあと消します（子を持っていたプロセスも同じです。子の親は
終わったときに付け替えてあります）。`waitpid` は
ありません。`spawn` のシステムコールで子を起動した親は、起動したスレッドで `child-exit` のメッセージ（`pid`・`code`・
`signal`）を受け取ります。終わったプロセスにシグナルを送ると `ESRCH` です。

### execve

`execve(argv, env, argv0)`（Node の `process.execve`。移植版ランタイム）は、プロセスのプログラムを入れ替えます。

- まず新しいプログラムを探します。`ENOENT`・`EACCES`・`ELOOP` のときは、プロセスに何もしません。
- 2 より大きい fd をすべて閉じ、監視を外し、古いプログラムのスレッドを止め、受け手を登録したシグナルの記録を消し、
  そのプロセスの TCP と Unix の待ち受けを放します。
- pid・ppid・プロセスグループ・`cwd`・fd 0〜2・制御 TTY・`nofile`・`umask` はそのままです。
- 新しいプログラムは、渡された `argv` と `env` で動きます。node のプログラムには、そのとき
  `/etc/openvessel/node` が選ぶランタイムを使います。

## プログラムの見つけ方

`argv[0]` は次のように解決します（`kernel.planExec`）。

1. **`/` を含む名前**はパスで、`cwd` からの相対です。あって、ディレクトリでないことが必要です。
2. **`/` を含まない名前**は、`PATH` の項目を順に探します（相対の項目は `cwd` から。POSIX のとおり、空の項目
   — `PATH=/bin:`・`PATH=:/bin`・`a::b` — は `cwd` そのものです）。`PATH` が無いときは `/bin:/usr/bin` です（glibc の
   `execvp`）。プロセスが実行できる最初の通常のファイルを使います（シンボリックリンクはたどります）。
3. **見つからない:** その名前の組み込みのプログラムが登録されていれば、それを動かします（`/bin` にファイルが
   無くても）。そうでなければ `ENOENT`、`<cmd>: command not found` です（シェルは 127 で終わります）。
4. **見つかった:** プロセスがそのファイルの実行の権限を持つ必要があります。無ければ `EACCES`、
   `<cmd>: Permission denied` です（シェルは 126 で終わります）。カーネルは先頭の 256 バイトを読みます。

| 最初の行・ファイル | 動かし方 |
|---|---|
| `#!/ov/builtin node` | node のプロセス（これが `/usr/bin/node`） |
| `#!/ov/builtin <name>` | 組み込みの `<name>`（登録が無ければ `ENOENT`、`<name>: builtin missing`） |
| `#!/usr/bin/env <arg>` または `#!/bin/env <arg>` | GNU の `env` が `<arg>` にすること（下を参照）のあと、`#!<command> [args]` と同じ。`<command>` は `PATH` で探す |
| `#!<interp> [arg]` で、`<interp>` の最後の名前が `node`・`nodejs`・`bun`・`deno` | node のプロセス: `node [arg] <file> <引数…>` |
| `#!<interp> [arg]`（それ以外） | `<interp> [arg] <file> <引数…>` を、手順 1 から解決し直す |
| `#!` が無く、ファイル名が `.js`・`.cjs`・`.mjs` で終わる | `node <file> <引数…>` |
| `#!` が無く、それ以外 | `sh <file> <引数…>`（POSIX のシェルが `ENOEXEC` のときにするのと同じ） |

- Linux と同じく、`#!` の行のインタプリタより後ろは（前後の空白を除いて）**1 つ**の引数として渡します。
  `#!/usr/bin/node --a --b` は `node '--a --b' <file>` を動かします。
- `#!/usr/bin/env`: `-S` が無ければ、引数は 1 つの単語です。`NAME=value` の代入か、コマンドの名前なので、
  `#!/usr/bin/env node --flag` は `node --flag` という名前のプログラムを探して `ENOENT` になります（Linux と同じ）。
  `-S` があれば（`#!/usr/bin/env -S node --flag`）、残りを GNU の `env -S` の決まり（空白、`'…'` と `"…"`、`\_`（空白）
  などのバックスラッシュのエスケープ、`${NAME}`、`#` のコメント）で単語に分けます。先頭のオプション `-i`・`-u NAME`・
  `--` と、続く `NAME=value` の単語はプログラムの環境変数に当て、その次の単語がコマンドです。
- インタプリタのつながりは、ファイル 9 つ（プログラムとインタプリタ 8 つ）までです。超えると `ELOOP` です。
- 無いインタプリタ（`#!/usr/bin/python3`）は `ENOENT` です。
- `node_modules/.bin` のパッケージのコマンドは、パッケージの bin のファイルへのシンボリックリンクで、インストーラーが
  実行できるようにしています。`#!/usr/bin/env node` の行で動きます。`.js` の決まりが見るのは、動かした名前で、
  シンボリックリンクの行き先ではありません。

```sh
printf '#!/usr/bin/env node\nconsole.log(process.argv.slice(2))\n' > hello
chmod +x hello
./hello a b          # [ 'a', 'b' ]
```

## 組み込みのプログラムと node のプロセス

| | 組み込みのプログラム | node のプロセス |
|---|---|---|
| 例 | `sh`・`ls`・`grep`・`npm`・`curl` | `node`・スクリプト・パッケージのコマンド |
| 動く場所 | カーネルの Worker の中の `async` 関数 | 自分の Web Worker |
| カーネルへの触れ方 | 直接（`ProgramContext`: fd・VFS・`spawn`） | [システムコール](kernel.ja.md#システムコール) を通して |
| 待つとき | カーネルを止めない。`await` で待つ | システムコールのあいだ、自分のスレッドを `Atomics.wait` で止める |
| シグナル | `onSignal` で受ける。受けなければ終わる（[シグナル](#シグナル)） | 受け手に届く。受け手が無ければ終わる |
| 起動にかかるもの | マイクロタスク 1 つ | 待機列の Worker と、Node.js の起動処理 |

## node のプロセスの起動

1. カーネルは、`/etc/openvessel/node` で選んだランタイムの Worker を取ります（`legacy` → 旧ランタイムの
   `process.js`、それ以外か無いとき → 既定の移植版ランタイムの `node-process.js`。プログラムの起動のときに読んでプロセスに記録し、
   そのプロセスのワーカースレッドも同じランタイムを使います）。ランタイムごとに、
   何もしていない Worker を 2 つ読み込んでおきます（[温めた Worker の待機列](kernel.ja.md#温めた-worker-の待機列)）。
2. そのスレッドのシステムコールのために、4 MiB の `SharedArrayBuffer` の通信路を作ります。
3. `init` を送ります。

| 項目 | 値 |
|---|---|
| `t` | `init` |
| `kind` | `main`（ワーカースレッドなら `thread`） |
| `pid`・`ppid`・`tid` | 番号 |
| `argv`・`env`・`cwd` | そのプロセスのもの |
| `sab` | システムコールの通信路 |
| `ttys` | fd 0, 1, 2 について、TTY なら `{ cols, rows }`、そうでなければ `null` |
| `hostname` | `openvessel` |
| スレッドの項目 | `file`・`eval`・`evalType`・`execArgv`・`workerData`・`envData`・`port`・`name`・`threadId`・`resourceLimits`・`envRings`・`trackUnmanagedFds`・`sharedEnv` |

そのあとランタイムが Node.js を起動し、プログラムを動かします。それ以外のこと（イベントループ、モジュール、
`process` のオブジェクト）はランタイムの受け持ちです（[Node.js のランタイム](nodejs-runtime.ja.md)）。

### ワーカースレッド

`worker_threads` は、同じプロセスの Worker を増やしたものです。pid も fd の表も `cwd` も同じです。

- ワーカースレッドの tid は `threadReserve` で取り、100000 から数えます。Node の `threadId` はプロセスごとに
  1, 2, … です。
- `threads × 8 + 30 > nofile` のとき、新しいスレッドを `EMFILE`（`initFailed`）で断ります（Node のスレッドは、
  それぞれ自分の記述子を持つためです）。既定の `nofile` 1024 では、1 つのプロセスのスレッドは 125 までです。
  `ulimit -n` は、そのあとシェルが起動するプロセスの上限を変えます。
- `threadKill`（`worker.terminate()`）は、スレッドをすぐに止めます（コード 1、`terminated: true` の `thread-exit`）。
- カーネルの返事は、頼んだスレッドへ返します。このため、メインスレッドが `Atomics.wait` で止まっているあいだも、
  ワーカースレッドは動き続けます。

## ファイル記述子と標準入出力

- 表はプロセスごとです。記述子は、参照の数を持つ共有のオープンファイル記述を指します。最後の参照が無くなると、
  そのオープンファイル記述は閉じます。
- 新しい記述子（`open`、親の側のパイプの端、受け付けた接続、受け取ったハンドル）は、空いている 3 以上の最小の番号を
  取ります。その番号は `nofile`（`RLIMIT_NOFILE`、`ulimit -n`）より小さい必要があり、届くときは `EMFILE` で失敗して
  何も作りません。既定の 1024 なら、0〜2 のほかに 1021 個の記述子を開けます。
- 子が受け継ぐのは、標準入出力として渡したものだけです。close-on-exec のフラグはありません。
- 移植版ランタイムの標準出力・標準エラー（fd 0〜2）への書き込みは、Linux の Node がパイプとファイルにするのと同じく、
  バッファ全体を同期で書きます。

### spawn のシステムコールの stdio

`stdio` は、子の fd の番号で並べた一覧です（既定は `['pipe', 'pipe', 'pipe']`）。

| 項目 | 子の fd | 親が受け取るもの |
|---|---|---|
| 位置 0 の `'pipe'`・`'overlapped'` | 新しいパイプの読む端 | 書く端（3 以上の fd） |
| 位置 1・2 の `'pipe'`・`'overlapped'` | 新しいパイプの書く端 | 読む端 |
| 位置 3 以上の `'pipe'`・`'overlapped'` | socketpair の片方（双方向） | もう片方 |
| `'ipc'` | socketpair の片方 | もう片方 |
| `'inherit'` | 親の同じ番号の fd（開いていなければ無し） | — |
| 数 `n` | 親の fd `n` | — |
| `'ignore'`・`null`・`undefined` | `/dev/null`（位置 0 は読み取り専用、ほかは書き込み専用） | — |
| それ以外 | fd 無し | — |

プログラムを起動できなかったときは、子の側の端を閉じます。`keepStdioOnError`（移植版ランタイムが使う）があれば、
`ENOENT`/`EACCES` を `{ pid: 0, fds, error }` として返し、親の側の端は開いたままにするので、libuv と同じく親の
ストリームは EOF を読みます。移植版ランタイムは Node のオプションを次のように変えます: `pipe` と `overlapped` →
`pipe`（または `ipc`）、`inherit` → `inherit`、`{ fd }` → その数、ハンドルを持つストリーム → その fd、それ以外 →
`ignore`。

### spawnSync

`spawnSync` は、子が終わり、出力の 2 つのパイプが閉じるまで、呼んだスレッドを止めます。

- 位置 0 の `'pipe'` は、渡した入力を受け取り、そのあと EOF です。位置 1 と 2 は出力を集めて返します。位置 3 以上は
  パイプを作り、読む端は捨てます。
- `'inherit'` と数は上と同じです。それ以外（`'ipc'` も）は `/dev/null` です。
- `timeout`（ミリ秒）: 子に `killSignal`（既定 `SIGTERM`）を送り、結果に `error: 'ETIMEDOUT'` を付けます。
- `maxBuffer` は、あとでランタイムが当てはめます（`ENOBUFS`）。

## パイプ

`createPipe()` は、読む端と書く端を持つ一方向のバイトの通り道を作ります（`src/kernel/io.ts`）。

| 性質 | ふるまい |
|---|---|
| バッファ | 大きさに上限の無いかたまりの列。ブロックする書き込みは、いつも全部のバイトを一度に受け取り、待たない |
| 容量 | 65536 バイト。ブロックしない書き手（`nonblock` 付きの `write`）にだけ効く。入る分だけ書き、いっぱいなら 0 |
| 背圧 | 移植版ランタイムは、標準入出力以外のパイプとソケットにブロックせずに書き、残りを列に入れて `fd-writable` を頼む。`fd-writable` はバッファがまた空になったとき（または読む人がいなくなったとき）に来る |
| 読み取り | たまっている分を、求めた大きさまで返す。何も無ければ待つ |
| EOF | 書く端がすべて閉じ、バッファが空のとき |
| 読み手がいない | 書き込みは `EPIPE` で失敗する。`SIGPIPE` は出さない。node のプロセスは `EPIPE` のエラーを受け取り（Node はもともと `SIGPIPE` を無視する）、組み込みのプログラムは 141 で終わる |
| 最後の読み手が閉じる | たまっていたデータは捨てる |
| プロセスへの送り出し | `readStart` のあと、データが来るたびに最大 64 KiB の `fd-data` を送り、EOF では `data: null` を送る |
| 番号 | パイプはそれぞれ番号を持ち、`readlink('/proc/self/fd/N')` で `pipe:[N]` と見える |

```sh
yes | head -2      # head が終わると、yes は EPIPE を受けて 141 で終わる
```

### socketpair

socketpair（`'ipc'` の標準入出力、追加の標準入出力のパイプ、TCP と Unix ソケットの接続）は、2 本のパイプを
交差させたものです。

- ブロックしない書き手への容量: 向きごとに 212992 バイト。
- `shutdown()` はこちらの端の書く側を閉じます。相手は EOF を読み、こちらはまだ読めます。
- 端を閉じると、両方の向きが閉じます。
- ハンドル（ソケット、サーバー、パイプ）は、データと一緒に送れます（`child.send(msg, handle)`）。その書き込みの最初の
  1 バイトに添えられ、そのバイトを読んだ読み手が受け取ります。ハンドルを求めずにそのバイトを読んだ読み手は、
  ハンドルを捨てます。

FIFO は [ファイルシステム](filesystem.ja.md#fifo) で説明しています。

## シグナル

### シグナルの表

カーネルは Linux のシグナルを知っています（`src/kernel/proc.ts`）。受け手が無いときは、signal(7) の既定の動作に
なります。

| シグナル | 番号 | 既定の動作 |
|---|---|---|
| `SIGHUP` | 1 | 終わる |
| `SIGINT` | 2 | 終わる |
| `SIGQUIT` | 3 | 終わる（core） |
| `SIGILL` | 4 | 終わる（core） |
| `SIGTRAP` | 5 | 終わる（core） |
| `SIGABRT`（`SIGIOT`） | 6 | 終わる（core） |
| `SIGBUS` | 7 | 終わる（core） |
| `SIGFPE` | 8 | 終わる（core） |
| `SIGKILL` | 9 | 終わる（受け手があっても） |
| `SIGUSR1` | 10 | 終わる |
| `SIGSEGV` | 11 | 終わる（core） |
| `SIGUSR2` | 12 | 終わる |
| `SIGPIPE` | 13 | 終わる |
| `SIGALRM` | 14 | 終わる |
| `SIGTERM` | 15 | 終わる |
| `SIGSTKFLT` | 16 | 終わる |
| `SIGCHLD`（`SIGCLD`） | 17 | 無視 |
| `SIGCONT` | 18 | 再開。止まっているものは無いので無視 |
| `SIGSTOP` | 19 | 停止。終わる（受け手があっても） |
| `SIGTSTP` | 20 | 停止。終わる |
| `SIGTTIN` | 21 | 停止。終わる |
| `SIGTTOU` | 22 | 停止。終わる |
| `SIGURG` | 23 | 無視 |
| `SIGXCPU` | 24 | 終わる（core） |
| `SIGXFSZ` | 25 | 終わる（core） |
| `SIGVTALRM` | 26 | 終わる |
| `SIGPROF` | 27 | 終わる |
| `SIGWINCH` | 28 | 無視（端末の大きさのため、node のプロセスにはメッセージを送る） |
| `SIGIO`（`SIGPOLL`） | 29 | 終わる |
| `SIGPWR` | 30 | 終わる |
| `SIGSYS`（`SIGUNUSED`） | 31 | 終わる（core） |
| `SIG32`・`SIG33` | 32・33 | 終わる |
| `SIGRTMIN`・`SIGRTMIN+1` … `SIGRTMIN+15`・`SIGRTMAX-14` … `SIGRTMAX-1`・`SIGRTMAX` | 34〜64 | 終わる |

名前は `kill -l` が出すものです。`SIG` の無い名前、括弧の中の別名、範囲内のどの書き方の `SIGRTMIN+n`/`SIGRTMAX-n`、
`SIG<番号>` も受け付けます。シグナルは、移植版ランタイムからは番号で、旧ランタイムからは名前で届きます。どちらでも
`process.kill(pid, 'SIGPWR')` は `SIGPWR` として届きます。

「終わる（core）」も「終わる」と同じように終わります（core ファイルは作りません）。止まった状態は無いので、停止の
シグナルもプロセスを終わらせ、`SIGCONT` で再開するものもありません。

### 届け方

- シグナルの受け手を持つ node のプロセス（`sigaction` を呼んだもの。`process.on('SIGINT', …)`）は、
  `{ t: 'signal', sig }` を受け取り、動き続けます。`SIGKILL` と `SIGSTOP` は受け手に届きません。
- 旧ランタイムが受け手を登録するのは `SIGINT`・`SIGTERM`・`SIGHUP`・`SIGQUIT`・`SIGUSR1`・`SIGUSR2`・`SIGWINCH`・
  `SIGBREAK`・`SIGPIPE`・`SIGCONT`・`SIGTSTP` です。移植版ランタイムは、Node の `process.on` が受け付けるすべての
  シグナルです。
- node のプロセスを終わらせると、その Worker をすぐに止めます。JavaScript はそれ以上動きません（`exit` のイベントも
  ありません）。
- 組み込みのプログラムは `onSignal` を置いて、シグナルを飲み込めます（対話のシェルは `SIGINT`・`SIGTSTP`・`SIGQUIT`・
  `SIGWINCH` を飲み込みます）。そうでなければ既定の動作になります。終わるときは `AbortSignal` が発火し、終了状態は
  すぐに決まり、プログラムがあとで返す値は無視します。

### kill

`kill { pid, sig }`（`process.kill`・`child.kill`）は kill(2) と同じです:

| `pid` | 相手 |
|---|---|
| `> 0` | そのプロセス |
| `0` | 呼んだプロセスのプロセスグループの、動いているすべてのプロセス（呼んだプロセスも含む） |
| `-1` | 呼んだプロセス以外の、動いているすべてのプロセス |
| `< -1` | グループ `-pid` の、動いているすべてのプロセス |

| `sig` | 効果 |
|---|---|
| `0` | 相手があって動いているかを調べるだけ |
| 1〜64 の数、またはシグナルの名前 | 上のとおりに、それぞれの相手に届ける（呼んだプロセスは最後） |
| それ以外 | `EINVAL` |

相手が無い、または終わっていれば（グループと `-1` では、動いているプロセスが 1 つも無ければ）`ESRCH` です。どの
プロセスも、ほかのどのプロセスにもシグナルを送れます（権限は調べません）。ホストの `kill(pid, signal)` は `pid` の
プロセスグループ全体に送り、失敗しません。

## プロセスグループとジョブ制御

- 新しいプロセスの `pgid`: 求められれば（`pgid: 0`）新しいグループ（`pgid = pid`）、そうでなく渡されればそのグループ、
  それも無ければ親のグループです。
- ホストが起動したプロセスは、自分のグループを持ちます。このため、ホストの `kill` は、そのプロセスと、それが同じ
  グループで起動したものすべてに届きます。
- 対話でないシェルでは、パイプラインのコマンドが新しいグループ 1 つ（最初に起動したコマンドの pid）を共有します。
  ほかのコマンドはシェルのグループのままです。対話のシェルは、コマンドをそれぞれ自分のグループで起動し、動いている
  あいだ TTY の前面のグループにします。
- キーボードからのシグナル（`^C`・`^\`・`^Z`）は、TTY の前面のグループへ送ります。
- ジョブ制御はありません。止まったジョブも `fg`/`bg` も無く、`jobs` は何も出しません。`^Z` は前面のジョブを
  終わらせます（終了状態 148）。
- セッションは無く、プログラムは自分のプロセスグループを変えられません（Node の `detached` のオプションは無視します）。

## 端末（TTY）

TTY は、ホストが端末付きでプロセスを起動したとき（`spawn(…, { terminal: { cols, rows } })`）に作ります。プロセスは
TTY を fd 0・1・2 として、制御端末として（子も受け継ぎます）、前面のグループの端末として受け取ります。出力は `output` の
イベントとしてホストへ送ります。

| 性質 | 値 |
|---|---|
| 大きさ | 渡さなければ `cols` 80、`rows` 24。ホストからの `resize(cols, rows)` で変わる |
| `SIGWINCH` | 大きさが変わるたびに、それを制御端末とする、動いているすべてのプロセスへ送る |
| 番号 | TTY ごとに 1, 2, …。`tty` のプログラムは `/dev/pts/<番号>` と出す |
| `isatty` | その TTY である fd なら true（`fstat` の mode は `S_IFCHR\|0620`） |
| `/dev/tty` | 制御端末を開く。無ければ `ENXIO` |

### 出力

出力は、raw のときも、1 つだけ変えて通します: 同じ書き込みの中で直前に CR の無い LF を CR LF にします（`ONLCR`）。

### 行の規律（cooked のとき）

入力は行に集め、行が終わったら読み手に渡します。

| 入力 | 効果 | エコー |
|---|---|---|
| 表示できるバイト、タブ | 行に足す | そのバイト |
| `CR`（13）または `LF`（10） | `LF` を足して行を渡す | `LF`（CR LF と表示） |
| `^C`（3） | 行を捨て、前面のグループに `SIGINT` | `^C` と改行 |
| `^\`（28） | 行を捨て、前面のグループに `SIGQUIT` | — |
| `^Z`（26） | 前面のグループに `SIGTSTP`（行はそのまま） | — |
| 空の行での `^D`（4） | ファイルの終わり。1 回の読み取りが EOF を返す | — |
| 行に文字があるときの `^D` | 改行を付けずに行を渡す | — |
| `DEL`（127）または `^H`（8） | 行の最後の UTF-8 の 1 文字を消す（空の行では何もしない） | `BS SP BS` |
| `^U`（21） | 行を捨てる（空の行では何もしない） | `CR` `ESC[K` |
| `ESC`（27） | 行に足す | —（そのあとのバイトはふつうにエコーする） |
| ほかの制御のバイト | 行に足す | — |

行の長さにも、読まれるのを待っている入力にも、上限はありません。ファイルの終わりは、それを受け取った 1 つの読み手が
使い切ります。

### raw とエコー

| 設定 | 効果 |
|---|---|
| `setRawMode(true)`（`process.stdin.setRawMode`） | raw にしてエコーを切る。バイトは来たとおりに読み手へ。`^C`・`^Z`・`^\`・`^D` もふつうのバイト |
| `setRawMode(false)` | raw をやめてエコーを入れる |
| `stty raw` / `stty -raw`・`stty sane`・`stty cooked` | raw にする / やめる（エコーは変えない） |
| `stty echo` / `stty -echo` | エコーを入れる / 切る |
| `stty size` | `<rows> <cols>` を出す |

対話のシェルの前面のコマンドが終わると、シェルは raw をやめ、エコーを入れます。

## 上限

| 上限 | 値 |
|---|---|
| プロセス | 上限なし。pid は使い回さない |
| プロセスごとの記述子 | `nofile` より小さい番号（超えると `EMFILE`） |
| `nofile`（`ulimit -n`） | 既定 1024。記述子とワーカースレッドを縛る: スレッドは `threads × 8 + 30 > nofile` のとき断る |
| インタプリタのつながり（`#!`） | ファイル 9 つ（`ELOOP`） |
| `#!` の行 | 先頭の 256 バイトから読む |
| `read` のシステムコール 1 回 | 16 MiB |
| システムコールの通信路 | スレッドごとに 4 MiB（大きいメッセージは何回かに分ける） |
| ブロックしない書き手へのパイプの容量 | 65536 バイト。socketpair は向きごとに 212992 バイト |
| `fd-data` の 1 回分 | 64 KiB |
| 終了時に読み手を待つ時間 | 250 ミリ秒 |
| 終わったプロセスを表に残す時間 | 60 秒 |
| CPU の時間・メモリ | カーネルには上限なし（ワーカースレッドは自分のランタイムに `resourceLimits` を渡せる） |
