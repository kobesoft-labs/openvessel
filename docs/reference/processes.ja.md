# プロセス

[English](processes.md)

OpenVessel のカーネルにおけるプロセスの仕様です。プロセスのライフサイクル、プログラムの検索と起動、ファイル記述子と
標準入出力、パイプとソケット、シグナル、プロセスグループ、端末（TTY）について説明します。ソースは
`src/kernel/kernel.ts`・`src/kernel/proc.ts`・`src/kernel/io.ts`・`src/kernel/syscalls.ts` です。

カーネル全体については [カーネル](kernel.ja.md)、シェルについては [シェル](shell.ja.md)、プロセスの中で動く Node.js
ランタイムについては [Node.js ランタイム](nodejs-runtime.ja.md) を参照してください。

## プロセスの記録

| 項目 | 意味 |
|---|---|
| `pid` | プロセス ID。カーネル全体で起動した順に 1, 2, 3, …。再利用しない |
| `ppid` | 親の pid。ホストが起動したプロセスと、親を失ったプロセスでは 0（init プロセスはなく、ホストがその役割を担う） |
| `pgid` | プロセスグループ（[プロセスグループ](#プロセスグループとジョブ制御)） |
| `argv` | 引数。node のプロセスの `argv[0]` は `node`（[argv0](#argv-と-env-と-cwd)） |
| `env` | 環境変数（文字列を値に持つ通常のオブジェクト） |
| `cwd` | 作業ディレクトリ（`chdir` の後は実パス） |
| `umask` | ファイル作成時のマスク。ホストが起動したプロセスは 0o022、それ以外は親から継承（[mode と umask](filesystem.ja.md#mode-と-umask)） |
| `nofile` | `RLIMIT_NOFILE`。1024 で、親から継承。シェルの `ulimit -n` で変更する |
| `runtime` | node のプロセスのみ。プログラムの起動時に選んだ Node.js ランタイム（[node のプロセスの起動](#node-のプロセスの起動)） |
| `fds` | ファイル記述子テーブル |
| `tty` | 制御端末。親から継承 |
| `kind` | `builtin`（カーネル内で動く）または `node`（Worker で動く） |
| `title` | `node`、または組み込みプログラムの名前 |
| `state`・`status` | `running` か `exited`。終了ステータスは `{ code, signal }` |
| `children` | 子プロセスの pid |
| `handledSignals` | プロセスがハンドラーを登録したシグナル |
| `threads` | node のプロセスの Node のスレッド（メインスレッドとワーカースレッド） |

ホストの `ps()` と `ps` コマンドは、実行中のプロセスだけを表示します（`PID`・`PPID`・`argv`）。

## 始まりから終わりまで

### 起動

`kernel.spawn()` は次の処理を同期的に行います。

1. 環境変数（指定されたもの、なければ親のコピー、それもなければ [既定の環境変数](kernel.ja.md#既定の環境変数)）と、
   作業ディレクトリ（指定されたもの、なければ親のもの、それもなければ `/home/user`）を決めます。
2. `argv` をどう実行するかを調べます（[プログラムの見つけ方](#プログラムの見つけ方)）。エラーは pid を割り当てる前の
   この段階で投げます。`ENOENT`（`<cmd>: command not found`）、`EACCES`（`<cmd>: Permission denied`）、
   `ELOOP`（インタプリタの連鎖が深すぎる）、`EINVAL`（`argv` が空）のいずれかです。
3. 次の pid を割り当て、プロセスグループ、制御 TTY、`nofile`、`umask` を設定し、指定された標準入出力の記述子を
   fd 0, 1, 2, … に設定します（それぞれ参照を 1 つ増やします）。
4. プログラムを開始します。組み込みプログラムはカーネルのイベントループ上で、node のプログラムは Worker で実行します
   （[node のプロセスの起動](#node-のプロセスの起動)）。

`spawn` システムコールは、これに加えて、指定された `cwd` が存在し、ディレクトリであることを確認します（`ENOENT`、
`spawn: cwd <path> does not exist`）。ホストの `spawn` は、`cwd` の指定がなければ `/home/user` を使い、そのディレクトリが
なければ作成します。

### argv と env と cwd

- 直接起動した node のプログラム（`node app.js`、または中身が `#!/ov/builtin node` のファイルのパス）は、呼び出し側の
  `argv[0]`（`process.argv0`。たとえば `node`）を引き継ぎます。`execve`/`spawn` では別の値（`argv0`）を渡すこともできます。
  スクリプトの `#!` 行を経由して起動した場合、`argv[0]` は `node` です。移植版ランタイムでは、`process.execPath` と
  `process.argv[0]` は `/usr/bin/node` になります。
- 環境変数は全体をそのまま渡します。子プロセスで、親の環境変数と指定された環境変数をマージすることはありません。
- `chdir` はシンボリックリンクを解決するので、新しい `cwd` は実パスになります。失敗した場合は `ENOENT` か `ENOTDIR` です。

### 終了

プロセスは次のいずれかで終了します。

| 終了のしかた | 終了ステータス |
|---|---|
| node のプロセスが `exit` を呼ぶ（`process.exit`、イベントループの終了） | `code & 0xff`（`process.exit(300)` は 44） |
| 組み込みプログラムが値を返す、または `ctx.exit(n)` を呼ぶ | `n` |
| 組み込みプログラムが例外を投げる | 標準エラーに `<name>: <message>` を出力し、1 |
| 組み込みプログラムが、誰も読んでいないパイプに書き込む（`EPIPE`） | 141 |
| シグナルで終了する | `{ code: null, signal }` |
| node のプロセスのメインの Worker が失敗する（`onerror`） | 1 |
| `process.abort()`（移植版ランタイム） | 134 |

node のプロセスが `exit` を呼ぶと、カーネルは終了処理の前に、読み手が追いつくのを待ちます。そのプロセスが書き込んだ
パイプを他のプロセスがまだ読んでいる場合は、パイプが空になるまで（最大 250 ミリ秒）待ちます。そのプロセスが書き込む
ソケットを他のプロセスが読んでいる場合は、それらのプロセスに `ping` を送り、`pong` を（最大 250 ミリ秒）待ちます。
終了しようとしているスレッドが再び動くことはありません。

その後、次の順に処理します。すべてのワーカースレッドを停止し、すべての fd を閉じ（パイプの読み手には EOF が返ります）、
待機しているものに通知し、そのプロセスの TCP と Unix ソケットの待ち受けを解放し（ホストに `port-closed` が届きます）、
監視と UDP のポートを削除し、子プロセスの親を pid 0 に付け替えます（そのプロセスの子ではなくなります）。

数値としての終了ステータス（`$?` やホストの `exit` イベントで見えるもの）は、終了コード、またはシグナルの場合は
`128 + シグナル番号` です（`SIGTERM` は `143`、`SIGINT` は `130`、`SIGPWR` は `158`）。

終了したプロセスの記録はプロセステーブルに 60 秒間残り、その後削除します（子を持っていたプロセスも同じです。子の親は
終了時に付け替え済みです）。`waitpid` はありません。`spawn` システムコールで子を起動した親は、起動したスレッドで
`child-exit` メッセージ（`pid`・`code`・`signal`）を受け取ります。終了したプロセスにシグナルを送ると `ESRCH` になります。

### execve

`execve(argv, env, argv0)`（Node の `process.execve`。移植版ランタイム）は、プロセスで実行するプログラムを置き換えます。

- まず新しいプログラムを探します。`ENOENT`・`EACCES`・`ELOOP` の場合、プロセスは変更しません。
- 2 より大きい fd をすべて閉じ、監視を削除し、古いプログラムのスレッドを停止し、ハンドラーを登録したシグナルの記録を
  消去し、そのプロセスの TCP と Unix の待ち受けを解放します。
- pid、ppid、プロセスグループ、`cwd`、fd 0〜2、制御 TTY、`nofile`、`umask` はそのまま残ります。
- 新しいプログラムは、指定された `argv` と `env` で実行します。node のプログラムには、その時点で `/etc/openvessel/node`
  が選択しているランタイムを使います。

## プログラムの見つけ方

`argv[0]` は次のように解決します（`kernel.planExec`）。

1. `/` を含む名前はパスとして扱い、`cwd` からの相対パスで解決します。存在し、ディレクトリでないことが必要です。
2. `/` を含まない名前は、`PATH` の各項目を順に探します。相対パスの項目は `cwd` を基準にし、空の項目（`PATH=/bin:`、
   `PATH=:/bin`、`a::b`）は POSIX の規定どおり `cwd` そのものを表します。`PATH` が未設定の場合は `/bin:/usr/bin` です
   （glibc の `execvp` と同じ）。プロセスが実行できる最初の通常ファイルを使います（シンボリックリンクはたどります）。
3. 見つからない場合、その名前の組み込みプログラムが登録されていれば、それを実行します（`/bin` にファイルがなくても
   実行します）。登録がなければ `ENOENT`、`<cmd>: command not found` です（シェルは 127 で終了します）。
4. 見つかった場合、プロセスがそのファイルの実行権限を持っている必要があります。なければ `EACCES`、
   `<cmd>: Permission denied` です（シェルは 126 で終了します）。カーネルはファイルの先頭 256 バイトを読みます。

| 最初の行・ファイル | 実行のしかた |
|---|---|
| `#!/ov/builtin node` | node のプロセス（これが `/usr/bin/node`） |
| `#!/ov/builtin <name>` | 組み込みの `<name>`（登録がなければ `ENOENT`、`<name>: builtin missing`） |
| `#!/usr/bin/env <arg>` または `#!/bin/env <arg>` | GNU の `env` が `<arg>` に対して行う処理（後述）の後、`#!<command> [args]` と同じ。`<command>` は `PATH` から探す |
| `#!<interp> [arg]` で、`<interp>` のベース名が `node`・`nodejs`・`bun`・`deno` | node のプロセス: `node [arg] <file> <引数…>` |
| `#!<interp> [arg]`（それ以外） | `<interp> [arg] <file> <引数…>` を手順 1 から解決し直す |
| `#!` がなく、ファイル名が `.js`・`.cjs`・`.mjs` で終わる | `node <file> <引数…>` |
| `#!` がなく、それ以外 | `sh <file> <引数…>`（POSIX のシェルが `ENOEXEC` のときに行うのと同じ） |

- Linux と同じく、`#!` 行のインタプリタより後ろの部分は（前後の空白を除いて）1 つの引数として渡します。
  `#!/usr/bin/node --a --b` は `node '--a --b' <file>` を実行します。
- `#!/usr/bin/env` で `-S` がない場合、引数は 1 つの単語で、`NAME=value` の代入かコマンド名のどちらかです。そのため
  `#!/usr/bin/env node --flag` は `node --flag` という名前のプログラムを探し、Linux と同じく `ENOENT` になります。
  `-S` がある場合（`#!/usr/bin/env -S node --flag`）は、残りを GNU の `env -S` のルール（空白、`'…'` と `"…"`、空白を表す
  `\_` などのバックスラッシュエスケープ、`${NAME}`、`#` のコメント）で単語に分割します。先頭のオプション `-i`・`-u NAME`・
  `--` と、それに続く `NAME=value` の単語はプログラムの環境変数に適用し、その次の単語をコマンドとします。
- インタプリタの連鎖は、ファイル 9 つ（プログラムとインタプリタ 8 つ）までです。超えると `ELOOP` になります。
- 存在しないインタプリタ（`#!/usr/bin/python3`）は `ENOENT` になります。
- `node_modules/.bin` にあるパッケージのコマンドは、パッケージの bin ファイルへのシンボリックリンクで、インストーラーが
  実行権限を付けています。これらは `#!/usr/bin/env node` 行で実行されます。`.js` のルールで見るのは実行時に指定した
  名前で、シンボリックリンクのリンク先ではありません。

```sh
printf '#!/usr/bin/env node\nconsole.log(process.argv.slice(2))\n' > hello
chmod +x hello
./hello a b          # [ 'a', 'b' ]
```

## 組み込みのプログラムと node のプロセス

| | 組み込みプログラム | node のプロセス |
|---|---|---|
| 例 | `sh`・`ls`・`grep`・`npm`・`curl` | `node`・スクリプト・パッケージのコマンド |
| 実行場所 | カーネルの Worker 内で `async` 関数として | 専用の Web Worker |
| カーネルへのアクセス | 直接（`ProgramContext`: fd・VFS・`spawn`） | [システムコール](kernel.ja.md#システムコール) 経由 |
| ブロッキング | カーネルをブロックしない。`await` で待つ | システムコールの間、自分のスレッドを `Atomics.wait` でブロックする |
| シグナル | `onSignal` フックで受け取る。なければ終了（[シグナル](#シグナル)） | ハンドラーに配送する。なければ終了 |
| 起動コスト | マイクロタスク 1 つ | プールにある待機中の Worker と、Node.js の起動処理 |

## node のプロセスの起動

1. カーネルは、`/etc/openvessel/node` で選択したランタイムの Worker を取得します。`legacy` なら旧ランタイムの
   `process.js`、それ以外またはファイルがない場合はデフォルトの移植版ランタイムの `node-process.js` です。この設定は
   プログラムの起動時に読み込んでプロセスに記録するので、そのプロセスのワーカースレッドも同じランタイムを使います。
   ランタイムごとに、アイドル状態の Worker を 2 つ読み込んでおきます（[温めた Worker の待機列](kernel.ja.md#worker-のウォームプール)）。
2. そのスレッドのシステムコール用に、4 MiB の `SharedArrayBuffer` のチャネルを作ります。
3. 次の項目を持つ `init` を送ります。

| 項目 | 値 |
|---|---|
| `t` | `init` |
| `kind` | `main`（ワーカースレッドなら `thread`） |
| `pid`・`ppid`・`tid` | 各 ID |
| `argv`・`env`・`cwd` | そのプロセスのもの |
| `sab` | システムコールのチャネル |
| `ttys` | fd 0, 1, 2 のそれぞれについて、TTY なら `{ cols, rows }`、そうでなければ `null` |
| `hostname` | `openvessel` |
| スレッド用の項目 | `file`・`eval`・`evalType`・`execArgv`・`workerData`・`envData`・`port`・`name`・`threadId`・`resourceLimits`・`envRings`・`trackUnmanagedFds`・`sharedEnv` |

その後、ランタイムが Node.js を起動してプログラムを実行します。イベントループ、モジュール、`process` オブジェクトなど、
それ以外の部分はランタイムが担当します（[Node.js ランタイム](nodejs-runtime.ja.md)）。

### ワーカースレッド

`worker_threads` は、同じプロセスに Worker を追加したものです。pid、fd テーブル、`cwd` は共通です。

- ワーカースレッドの tid は `threadReserve` で予約し、100000 から数えます。Node の `threadId` はプロセスごとに
  1, 2, … と数えます。
- `threads × 8 + 30 > nofile` のときは、新しいスレッドを `EMFILE`（`initFailed`）で拒否します（Node のスレッドは
  それぞれ専用の記述子を持つためです）。デフォルトの `nofile` 1024 では、1 プロセスあたり最大 125 スレッドです。
  `ulimit -n` を変更すると、それ以降にシェルが起動するプロセスの上限が変わります。
- `threadKill`（`worker.terminate()`）はスレッドをすぐに終了します（コード 1、`terminated: true` の `thread-exit`）。
- カーネルの応答は要求したスレッドに返します。そのため、メインスレッドが `Atomics.wait` でブロックしている間も、
  ワーカースレッドは動き続けます。

## ファイル記述子と標準入出力

- テーブルはプロセスごとに持ちます。記述子は、参照カウントを持つ共有のオープンファイル記述を指し、最後の参照が
  なくなるとオープンファイル記述を閉じます。
- 新しい記述子（`open`、親側のパイプの端、受け付けた接続、受け取ったハンドル）には、空いている 3 以上の最小の番号を
  割り当てます。その番号は `nofile`（`RLIMIT_NOFILE`、`ulimit -n`）より小さい必要があり、上限に達した場合は `EMFILE` で
  失敗して何も作りません。デフォルトの 1024 では、0〜2 のほかに 1021 個の記述子を開けます。
- 子プロセスが継承するのは、標準入出力として渡したものだけです。close-on-exec フラグはありません。
- 移植版ランタイムでは、標準出力・標準エラー（fd 0〜2）への書き込みはバッファ全体を同期的に書き込みます。Linux の
  Node がパイプとファイルに対して行うのと同じ動作です。

### spawn のシステムコールの stdio

`stdio` は、子の fd 番号をインデックスとする配列です（デフォルトは `['pipe', 'pipe', 'pipe']`）。

| 項目 | 子の fd | 親が受け取るもの |
|---|---|---|
| インデックス 0 の `'pipe'`・`'overlapped'` | 新しいパイプの読み取り側 | 書き込み側（3 以上の fd） |
| インデックス 1・2 の `'pipe'`・`'overlapped'` | 新しいパイプの書き込み側 | 読み取り側 |
| インデックス 3 以上の `'pipe'`・`'overlapped'` | socketpair の一方（双方向） | もう一方 |
| `'ipc'` | socketpair の一方 | もう一方 |
| `'inherit'` | 親の同じ番号の fd（開いていなければなし） | — |
| 数値 `n` | 親の fd `n` | — |
| `'ignore'`・`null`・`undefined` | `/dev/null`（インデックス 0 は読み取り専用、それ以外は書き込み専用） | — |
| それ以外 | fd なし | — |

プログラムを起動できなかった場合は、子側の端を閉じます。`keepStdioOnError`（移植版ランタイムが使用）を指定した場合は、
`ENOENT`/`EACCES` を `{ pid: 0, fds, error }` として返し、親側の端は開いたままにします。そのため、libuv と同じく親の
ストリームは EOF を読みます。移植版ランタイムは Node のオプションを次のように変換します。`pipe` と `overlapped` →
`pipe`（または `ipc`）、`inherit` → `inherit`、`{ fd }` → その数値、ハンドルを持つストリーム → その fd、それ以外 →
`ignore` です。

### spawnSync

`spawnSync` は、子プロセスが終了し、2 つの出力パイプが閉じるまで、呼び出したスレッドをブロックします。

- インデックス 0 の `'pipe'` は、指定した入力を受け取った後に EOF になります。インデックス 1 と 2 は出力を集めて返します。
  インデックス 3 以上ではパイプを作り、読み取り側は捨てます。
- `'inherit'` と数値は上と同じです。それ以外（`'ipc'` を含む）は `/dev/null` になります。
- `timeout`（ミリ秒）を過ぎると、子に `killSignal`（デフォルトは `SIGTERM`）を送り、結果に `error: 'ETIMEDOUT'` を付けます。
- `maxBuffer` は、その後ランタイムが適用します（`ENOBUFS`）。

## パイプ

`createPipe()` は、読み取り側と書き込み側を持つ一方向のバイトストリームを作ります（`src/kernel/io.ts`）。

| 性質 | 動作 |
|---|---|
| バッファ | サイズ上限のないチャンクのリスト。ブロッキングの書き込みは常に全バイトを一度に受け取り、待つことはない |
| 容量 | 65536 バイト。ノンブロッキングの書き手（`nonblock` 付きの `write`）にだけ適用される。入る分だけ書き込み、満杯なら 0 が返る |
| 背圧 | 移植版ランタイムは、標準入出力以外のパイプとソケットにノンブロッキングで書き込み、残りをキューに入れて `fd-writable` を要求する。`fd-writable` はバッファが再び空になったとき（または読み手がいなくなったとき）に届く |
| 読み取り | バッファにある分を、要求したサイズまで返す。何もなければ待つ |
| EOF | すべての書き込み側が閉じ、バッファが空になったとき |
| 読み手がいない | 書き込みは `EPIPE` で失敗する。`SIGPIPE` は発生しない。node のプロセスは `EPIPE` エラーを受け取り（Node はもともと `SIGPIPE` を無視する）、組み込みプログラムはステータス 141 で終了する |
| 最後の読み手が閉じる | バッファにあるデータを捨てる |
| プロセスへのプッシュ | `readStart` の後、データが届くたびに最大 64 KiB の `fd-data` メッセージを送り、EOF では `data: null` を送る |
| 識別番号 | パイプはそれぞれ番号を持ち、`readlink('/proc/self/fd/N')` では `pipe:[N]` と表示される |

```sh
yes | head -2      # head が終了すると、yes は EPIPE を受け取ってステータス 141 で終了する
```

### socketpair

socketpair（`'ipc'` の標準入出力、追加の標準入出力のパイプ、TCP と Unix ソケットの接続）は、2 本のパイプを交差させた
ものです。

- ノンブロッキングの書き手に対する容量は、方向ごとに 212992 バイトです。
- `shutdown()` はこちら側の書き込みを閉じます。相手側は EOF を読み、こちら側は引き続き読み取りができます。
- 一方の端を閉じると、両方向とも閉じます。
- ハンドル（ソケット、サーバー、パイプ）はデータと一緒に送れます（`child.send(msg, handle)`）。ハンドルはその書き込みの
  最初の 1 バイトに付加され、そのバイトを読んだ読み手が受け取ります。ハンドルを要求せずにそのバイトを読んだ読み手は、
  ハンドルを捨てます。

FIFO については [ファイルシステム](filesystem.ja.md#fifo) で説明しています。

## シグナル

### シグナルの表

カーネルは Linux のシグナルに対応しています（`src/kernel/proc.ts`）。ハンドラーがない場合は、signal(7) のデフォルトの
動作になります。

| シグナル | 番号 | デフォルトの動作 |
|---|---|---|
| `SIGHUP` | 1 | 終了 |
| `SIGINT` | 2 | 終了 |
| `SIGQUIT` | 3 | 終了（core） |
| `SIGILL` | 4 | 終了（core） |
| `SIGTRAP` | 5 | 終了（core） |
| `SIGABRT`（`SIGIOT`） | 6 | 終了（core） |
| `SIGBUS` | 7 | 終了（core） |
| `SIGFPE` | 8 | 終了（core） |
| `SIGKILL` | 9 | 終了（ハンドラーがあっても） |
| `SIGUSR1` | 10 | 終了 |
| `SIGSEGV` | 11 | 終了（core） |
| `SIGUSR2` | 12 | 終了 |
| `SIGPIPE` | 13 | 終了 |
| `SIGALRM` | 14 | 終了 |
| `SIGTERM` | 15 | 終了 |
| `SIGSTKFLT` | 16 | 終了 |
| `SIGCHLD`（`SIGCLD`） | 17 | 無視 |
| `SIGCONT` | 18 | 再開（停止中のものがないので無視） |
| `SIGSTOP` | 19 | 停止（終了する。ハンドラーがあっても） |
| `SIGTSTP` | 20 | 停止（終了する） |
| `SIGTTIN` | 21 | 停止（終了する） |
| `SIGTTOU` | 22 | 停止（終了する） |
| `SIGURG` | 23 | 無視 |
| `SIGXCPU` | 24 | 終了（core） |
| `SIGXFSZ` | 25 | 終了（core） |
| `SIGVTALRM` | 26 | 終了 |
| `SIGPROF` | 27 | 終了 |
| `SIGWINCH` | 28 | 無視（端末サイズのため、node のプロセスにはメッセージを送る） |
| `SIGIO`（`SIGPOLL`） | 29 | 終了 |
| `SIGPWR` | 30 | 終了 |
| `SIGSYS`（`SIGUNUSED`） | 31 | 終了（core） |
| `SIG32`・`SIG33` | 32・33 | 終了 |

名前は `kill -l` で表示されるものです。カーネルは、`SIG` を省いた名前、括弧内の別名、範囲内のどの表記の
`SIGRTMIN+n`/`SIGRTMAX-n`、`SIG<番号>` も受け付けます。シグナルは、移植版ランタイムからは番号で、旧ランタイムからは
名前でチャネルを通ります。どちらの場合も、`process.kill(pid, 'SIGPWR')` は `SIGPWR` として届きます。

「終了（core）」は「終了」と同じようにプロセスを終了します（core ダンプは作りません）。停止状態はないので、停止の
シグナルもプロセスを終了させ、`SIGCONT` で再開する対象もありません。

### 届け方

- シグナルのハンドラーを持つ node のプロセス（`sigaction` を呼んだもの。たとえば `process.on('SIGINT', …)`）は、
  `{ t: 'signal', sig }` を受け取り、そのまま動き続けます。`SIGKILL` と `SIGSTOP` がハンドラーに配送されることは
  ありません。
- 旧ランタイムがハンドラーを登録するのは `SIGINT`・`SIGTERM`・`SIGHUP`・`SIGQUIT`・`SIGUSR1`・`SIGUSR2`・`SIGWINCH`・
  `SIGBREAK`・`SIGPIPE`・`SIGCONT`・`SIGTSTP` です。移植版ランタイムは、Node の `process.on` が受け付けるすべての
  シグナルに対して登録します。
- node のプロセスを終了させると、その Worker をすぐに停止します。それ以降 JavaScript は実行されません（`exit` イベントも
  発生しません）。
- 組み込みプログラムは `onSignal` を設定して、シグナルを握りつぶすことができます（対話シェルは `SIGINT`・`SIGTSTP`・
  `SIGQUIT`・`SIGWINCH` を握りつぶします）。設定がなければデフォルトの動作になります。デフォルトの動作で終了する場合は、
  プログラムの `AbortSignal` が発火して終了ステータスがすぐに確定し、プログラムが後から返す値は無視します。

### kill

`kill { pid, sig }`（`process.kill`・`child.kill`）は kill(2) と同じ動作です。`pid` で対象を指定します。

| `pid` | 対象 |
|---|---|
| `> 0` | そのプロセス |
| `0` | 呼び出したプロセスのプロセスグループに属する、実行中のすべてのプロセス（呼び出したプロセスを含む） |
| `-1` | 呼び出したプロセス以外の、実行中のすべてのプロセス |
| `< -1` | グループ `-pid` に属する、実行中のすべてのプロセス |

`sig` は次のように扱います。

- `0` は、対象が存在して実行中であるかを確認するだけです。
- 1〜64 の数値、またはシグナルの名前は、上で説明したとおりに各対象へ配送します（呼び出したプロセスは最後）。
- それ以外は `EINVAL` になります。

対象が存在しない、または終了している場合は `ESRCH` になります。グループや `-1` の場合は、実行中のプロセスが 1 つも
ないときに `ESRCH` です。どのプロセスも他のどのプロセスにもシグナルを送れます（権限の確認はありません）。ホストの
`kill(pid, signal)` は `pid` のプロセスグループ全体にシグナルを送り、失敗することはありません。

## プロセスグループとジョブ制御

- 新しいプロセスは、要求があれば（`pgid: 0`）新しいグループ（`pgid = pid`）に、グループが指定されていればそのグループに、
  どちらでもなければ親のグループに属します。
- ホストが起動したプロセスは専用のグループを持ちます。そのため、ホストの `kill` は、そのプロセスと、そのプロセスが同じ
  グループで起動したすべてのプロセスに届きます。
- 非対話シェルでは、パイプラインのコマンドが 1 つの新しいグループ（最初に起動したコマンドの pid）を共有し、それ以外の
  コマンドはシェルのグループに残ります。対話シェルは、各コマンドを専用のグループで起動し、実行中はそのグループを TTY の
  フォアグラウンドグループにします。
- キーボードからのシグナル（`^C`・`^\`・`^Z`）は、TTY のフォアグラウンドグループに送ります。
- ジョブ制御はありません。停止したジョブも `fg`/`bg` もなく、`jobs` は何も表示しません。`^Z` はフォアグラウンドの
  ジョブを終了させます（終了ステータス 148）。
- セッションはなく、プログラムが自分のプロセスグループを変更することはできません（Node の `detached` オプションは
  無視します）。

## 端末（TTY）

TTY は、ホストが端末付きでプロセスを起動したとき（`spawn(…, { terminal: { cols, rows } })`）に作成します。プロセスは
TTY を fd 0・1・2 として、制御端末として（子プロセスにも継承されます）、またフォアグラウンドグループの端末として
受け取ります。出力は `output` イベントとしてホストに送ります。

| 性質 | 値 |
|---|---|
| サイズ | 指定がなければ `cols` 80、`rows` 24。ホストからの `resize(cols, rows)` で変更する |
| `SIGWINCH` | サイズが変わるたびに、その TTY を制御端末とする実行中のすべてのプロセスに送る |
| ID | TTY ごとに 1, 2, …。`tty` コマンドは `/dev/pts/<ID>` を表示する |
| `isatty` | その TTY である fd なら true（`fstat` の mode は `S_IFCHR\|0620`） |
| `/dev/tty` | 制御端末を開く。制御端末がなければ `ENXIO` |

### 出力

出力は、raw モードのときも含めて、1 点だけ変換して渡します。同じ書き込みの中で直前に CR がない LF を CR LF に変換します
（`ONLCR`）。

### 行の規律（cooked のとき）

入力は 1 行分ためておき、行が終わった時点で読み手に渡します。

| 入力 | 効果 | エコー |
|---|---|---|
| 表示可能なバイト、タブ | 行に追加 | そのバイト |
| `CR`（13）または `LF`（10） | `LF` を追加して行を渡す | `LF`（CR LF として表示） |
| `^C`（3） | 行を破棄し、フォアグラウンドグループに `SIGINT` | `^C` と改行 |
| `^\`（28） | 行を破棄し、フォアグラウンドグループに `SIGQUIT` | — |
| `^Z`（26） | フォアグラウンドグループに `SIGTSTP`（行はそのまま） | — |
| 空の行での `^D`（4） | ファイルの終わり。1 回の読み取りが EOF を返す | — |
| 行に文字があるときの `^D` | 改行を付けずに行を渡す | — |
| `DEL`（127）または `^H`（8） | 行の最後の UTF-8 の 1 文字を削除（空の行では何もしない） | `BS SP BS` |
| `^U`（21） | 行を破棄（空の行では何もしない） | `CR` `ESC[K` |
| `ESC`（27） | 行に追加 | —（その後のバイトは通常どおりエコーする） |
| その他の制御バイト | 行に追加 | — |

行の長さにも、読み取りを待っている入力の量にも上限はありません。ファイルの終わりは、それを受け取った 1 つの読み手だけが
消費します。

### raw とエコー

| 設定 | 効果 |
|---|---|
| `setRawMode(true)`（`process.stdin.setRawMode`） | raw をオン、エコーをオフにする。バイトは届いたとおりに読み手へ渡り、`^C`・`^Z`・`^\`・`^D` も通常のバイトとして扱う |
| `setRawMode(false)` | raw をオフ、エコーをオンにする |
| `stty raw` / `stty -raw`・`stty sane`・`stty cooked` | raw をオン / オフにする（エコーは変更しない） |
| `stty echo` / `stty -echo` | エコーをオン / オフにする |
| `stty size` | `<rows> <cols>` を表示する |

対話シェルのフォアグラウンドのコマンドが終了すると、シェルは raw をオフ、エコーをオンに戻します。

## 上限

| 上限 | 値 |
|---|---|
| プロセス | 上限なし（pid は再利用しない） |
| プロセスごとの記述子 | `nofile` より小さい番号（超えると `EMFILE`） |
| `nofile`（`ulimit -n`） | デフォルトは 1024。記述子とワーカースレッドを制限する（`threads × 8 + 30 > nofile` のときスレッドを拒否） |
| インタプリタの連鎖（`#!`） | ファイル 9 つ（`ELOOP`） |
| `#!` 行 | 先頭 256 バイトから読む |
| `read` システムコール 1 回 | 16 MiB |
| システムコールのチャネル | スレッドごとに 4 MiB（大きなメッセージは複数回に分ける） |
| ノンブロッキングの書き手に対するパイプの容量 | 65536 バイト（socketpair は方向ごとに 212992 バイト） |
| `fd-data` の 1 回分 | 64 KiB |
| 終了時に読み手を待つ時間 | 250 ミリ秒 |
| 終了したプロセスをテーブルに残す時間 | 60 秒 |
| CPU 時間・メモリ | カーネルでは制限しない（ワーカースレッドは自分のランタイムに `resourceLimits` を渡せる） |
